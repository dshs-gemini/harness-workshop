# 02. 슬라이드 원고: 모듈 7. 배포·보안 규칙·마무리 (슬라이드 47–54)

## 가정
- 번호 범위(47–54, 8장), 시간(25분 = 배포·보안 20 + 마무리 5)은 모듈 2 확장(+5분) 상쇄 요청으로 마무리를 10분에서 5분으로 줄인 값이다.
- 참가자의 프로젝트에는 `checkpoint-m6` 수준의 기능(로그인, 수업코드, 자료, 학습지, 피드백)이 이미 있고, 모듈 2의 임시 규칙이 걸려 있다고 가정한다.
- 수업코드 조회(원칙 4)는 practice-engineer의 결정 D1을 따른다. 수업 문서 이름(classId)이 수업코드(joinCode)이고, 학생은 `classes/{코드}` 1건만 읽는다(get). 목록(list)은 내가 교사인 수업만 허용한다. 모듈 3 슬라이드 21·22 프롬프트는 이 방식으로 교체되어 있다(M3 원고 반영됨).
- members 문서에는 `uid` 필드가 있다(D2, 명세 반영됨, 2026-10-03).
- 슬라이드 48의 `feedback` 쓰기 제한은 D4로 확정됐다(학생은 answers, submittedAt만 바꾼다).
- 권한 판정(D3): 수업 만들기(create)에서만 `users.role`을 확인하고 role은 처음 저장 뒤 바꿀 수 없다. 그 밖의 권한은 모두 `teacherUid`로 판정한다.
- 슬라이드 50·51의 검증은 강사가 `checkpoint-final`에 넣어 둔 규칙 점검 페이지 `rules-check.html`(버튼 1~6 막힘 + 확인 버튼 열림 2건)로 한다. 점검 전 수업 2개(A, B) 준비와 B 가입·학습지 제출은 슬라이드 49~50 사이 또는 휴식에 미리 해 두어 슬라이드 50의 5분에 점검만 들어가게 한다.
- 슬라이드별 시간: 47(3) + 48(4) + 49(4) + 50(5) + 51(4) = 20분, 52(2) + 53(2) + 54(1) = 5분, 합계 25분.
- 검수 대상 표시: 슬라이드 48의 규칙 결과물은 데이터 모델 경로와의 일치 여부를 **content-reviewer가 반드시 검수**한다.

## [슬라이드 47] 보안 규칙 = 교무실 출입 규칙
- 유형: 개념
- 본문:
  - 보안 규칙은 교무실 출입 규칙이다. 누가 어떤 서류함을 열 수 있는지 정한다.
  - 지금까지 5가지 원칙을 하나씩 만났다. 오늘 한 번에 걸어 잠근다.
  - 화면 버튼을 숨기는 것은 안전이 아니다. 규칙이 막아야 진짜 막힌다.
- 도식: 5행 요약표. 열은 "원칙 / 한 줄 뜻 / 처음 만난 곳".
  1. 가입한 수업 자료만 읽는다 / 열쇠 없으면 교실 못 들어감 / 슬라이드 28
  2. 내 제출물만 읽고 쓴다 / 내 답안지만 열람 / 슬라이드 34, 41
  3. 수업·자료·학습지 작성은 그 수업 교사만 / 교사만 교실을 꾸밈 / 슬라이드 20
  4. 수업코드를 아는 사람만 그 수업 1건을 찾는다, 전체 목록은 못 본다 / 열쇠로 문 하나만 열기 / 슬라이드 20
  5. 교사 HTML은 sandbox iframe으로 / 유리 진열장 / 슬라이드 28
  오른쪽에 "교무실 문" 그림. 원칙 1–4는 규칙(서버 쪽)이 지키고, 원칙 5는 화면(iframe)이 지킨다는 구분 표시.
- 노트: (3분) "Firestore는 학급 서류함이라고 했습니다. 이 서류함에 자물쇠를 거는 문서가 보안 규칙입니다. 지금까지 모듈마다 한 줄씩 소개한 원칙 다섯 개를 표로 모았습니다. 지금은 외우지 않아도 됩니다. 다음 장에서 이 문장을 그대로 Claude Code에 넘깁니다." 원칙 4 정확한 범위: 규칙은 "가입할 때"를 구분하지 못한다. 수업코드를 아는 로그인 사용자는 언제든 그 수업 1건을 조회할 수 있다(코드가 열쇠). 포인트: 역할(teacher/student)은 화면 분기용이고, 수업이 만들어진 뒤의 권한은 `classes/{classId}.teacherUid`로 판정한다고 말한다. 예외는 수업을 새로 만드는 순간 한 곳이다. 이때만 교사 계정인지 role을 확인하고, role은 한 번 정하면 바꿀 수 없다. 원칙 5는 규칙 파일이 아니라 iframe 속성으로 지킨다는 점도 짚는다.

## [슬라이드 48] 5원칙을 문장으로 주고 규칙 파일 만들기
- 유형: 실습
- 본문:
  - 보안 규칙 파일(`firestore.rules`)도 Claude Code가 쓴다.
  - 우리는 원칙을 문장으로 주고, 줄마다 몇 번 원칙인지 설명을 요청한다.
  - 규칙이 쓰는 경로는 우리 데이터 모델과 같아야 한다.
- 프롬프트:
```
이 프로젝트의 firestore.rules 파일을 새로 작성해 줘. 기존 임시 규칙은 모두 지우고 아래 원칙만 적용해 줘. 기본은 모든 접근 거부이고, 아래에서 허용한 것만 열어 줘.

데이터 경로는 이 이름 그대로 써 줘.
- users/{uid}: name, email, role
- classes/{classId}: title, teacherUid, joinCode (문서 이름 classId는 수업코드 joinCode와 같다)
- classes/{classId}/members/{uid}: joinedAt, uid
- classes/{classId}/materials/{id}: title, html, createdAt
- classes/{classId}/worksheets/{id}: title, questions[]
- classes/{classId}/worksheets/{id}/submissions/{uid}: answers, feedback, submittedAt

원칙
1. 학생은 자신이 가입한 수업(내 uid의 members 문서가 있는 수업)의 자료와 학습지만 읽는다.
2. 학생은 자기 제출물(문서 이름이 내 uid인 submissions 문서)만 읽고 쓴다. 다른 학생의 제출물은 읽을 수 없고 제출물 목록도 볼 수 없다. 학생은 자기 제출물에서 answers와 submittedAt만 바꿀 수 있고 feedback 필드는 만들거나 고치거나 지울 수 없다.
3. 수업, 자료, 학습지를 고치고 지우는 것과 자료·학습지를 만드는 것은 해당 수업의 teacherUid와 내 uid가 같은 교사만 한다. 수업을 새로 만드는 것만 users 문서의 role이 teacher인 사람에게 허용하고, teacherUid는 반드시 내 uid여야 한다. role은 처음 저장한 뒤 바꿀 수 없게 해 줘. 그 밖의 권한은 role로 판단하지 마. 해당 수업 교사는 그 수업의 가입자 명단과 제출물을 읽고, 제출물의 feedback 필드만 쓸 수 있다.
4. 수업 목록 조회(list)는 내가 teacherUid인 수업만 허용하고, 학생이 수업 목록 전체를 가져오는 것은 막는다. 수업 문서 이름이 수업코드이므로, 코드를 아는 사람이 classes/{코드} 한 건을 읽는 것(get)과 그 수업 members에 내 uid 문서를 만드는 것은 허용한다. 학생은 members 컬렉션 그룹 조회로 uid가 내 uid인 가입 문서만 찾을 수 있다.
5. 이 원칙은 규칙이 아니라 화면 쪽 일이야. 규칙 파일에는 넣지 말고, 자료를 보여주는 iframe에 sandbox 속성이 있는지 index.html이나 app.js에서 확인만 해 줘.

그리고 규칙의 각 match 블록과 allow 줄 위에 "이 줄은 원칙 N번" 하는 한국어 주석을 달아 줘. 마지막에 원칙 1~5가 각각 어느 줄에 해당하는지 표로 정리해 줘. 초등학교 교사가 읽어도 이해할 수 있게 써 줘.
```
- 예상 결과: `firestore.rules` 파일이 새로 생기고, 줄마다 "원칙 N번" 주석이 달려 있다. Claude Code가 원칙 1–4가 어느 줄인지 표로 알려 주고, 원칙 5(sandbox)는 화면 코드에서 확인한 결과를 보고한다.
- 막힐 때:
  - 규칙 문법이 이상하다고 나오면: Claude Code에 "firestore.rules 문법 오류가 없는지 확인하고 고쳐 줘"라고 요청한다.
  - 규칙에 `role == 'teacher'` 같은 줄이 수업 만들기(classes의 create) 말고 다른 곳에 있으면: "권한은 role이 아니라 해당 수업의 teacherUid로 판단하도록 고쳐 줘. role은 수업을 새로 만들 때만 확인해 줘"라고 다시 요청한다. 수업 만들기에 role 확인이 있는 것은 정상이다.
- 노트: (4분, 설명 1 + 실습 3) "코드를 읽을 필요는 없습니다. 대신 '원칙 N번' 주석이 5개 원칙을 모두 덮는지만 확인하세요." 확인 기준은 (1) 맨 처음 기본 거부가 있는가 (2) 원칙 1–4 주석이 모두 있는가 (3) role을 보는 곳이 수업 만들기(create)와 role 변경 금지뿐인가. 수업코드가 곧 수업 문서 이름이라는 점은 모듈 3에서 이미 그렇게 만들었다. 모듈 3을 where 조회로 만든 참가자는 최종 규칙 배포 뒤 학생 가입이 실패하므로, 그 경우 슬라이드 50 "막힐 때"와 `checkpoint-final`로 안내한다. `[재확인 필요: 원칙 4 구현(문서 이름=수업코드, get 허용·list 제한) 일치. 근거였던 에뮬레이터 테스트 파일이 삭제됨]` `[재확인 필요: 원칙 2 feedback 쓰기 제한(학생은 answers·submittedAt만). 같은 이유]` **content-reviewer 검수 대상**: 규칙의 경로가 데이터 모델과 글자 하나까지 일치하는가. 막힌 참가자에게는 강사가 `checkpoint-final`의 `firestore.rules`를 복사하게 해도 된다.

## [슬라이드 49] 규칙과 웹사이트를 인터넷에 올리기
- 유형: 실습
- 본문:
  - 규칙 배포는 출입 규칙을 교무실 문에 붙이는 일이다.
  - Hosting 배포는 우리 클래스룸을 학교 게시판에 올리는 일이다.
  - 끝나면 누구나 열 수 있는 공개 주소가 생긴다. 규칙·색인 파일은 공개하지 않는다.
- 프롬프트:
```
firestore.rules를 Firebase에 배포하고, 이어서 이 프로젝트를 Firebase Hosting에 배포해 줘. 순서는 아래와 같이 해 줘.
1. firebase.json에 firestore 규칙 파일(firestore.rules), 색인 파일(firestore.indexes.json), hosting 설정(현재 폴더를 그대로 공개)이 맞게 들어 있는지 확인하고, 없으면 추가해 줘. 빌드 도구가 없는 정적 웹이라서 현재 폴더를 그대로 올리면 돼. firebase.json, firestore.rules, firestore.indexes.json, README.md, samples 폴더, functions 폴더(있으면), 숨김 파일은 공개하지 않도록 hosting의 ignore에 넣어 줘.
2. 연결할 Firebase 프로젝트 ID는 firebase-config.js의 projectId 값을 써 줘.
3. Firebase CLI에 로그인이 안 되어 있으면 나에게 로그인 방법을 알려 줘.
4. 규칙과 색인을 먼저 배포해 줘. 이어서 Hosting을 배포해 줘.
5. 배포가 끝나면 공개 주소(Hosting URL)를 알려 줘. 오류가 나면 오류 메시지를 쉬운 말로 설명하고 고쳐 줘.
```
- 예상 결과: 터미널에 규칙·색인 배포 성공 메시지와 Hosting 배포 성공 메시지가 나오고, `https://프로젝트ID.web.app` 형태의 공개 주소가 표시된다 `[확인필요: 주소 형식]`. 주소를 크롬에서 열면 로그인 화면이 보인다.
- 막힐 때:
  - 로그인 또는 권한 오류가 나면: 터미널에서 Firebase CLI 로그인을 다시 하라고 Claude Code가 안내한다. 로그인은 브라우저 창이 열리는 대화형 명령이라 Claude Code가 대신 끝내지 못할 수 있으니, 안내받은 명령을 참가자가 터미널(또는 Claude Code 입력창에서 `!` 뒤에)에서 직접 실행하고 브라우저에서 구글 계정을 선택한다 `[확인필요: CLI 로그인 명령, Claude Code의 셸 명령 입력 방식]`.
  - 규칙 배포에서 "프로젝트가 선택되지 않음" 오류가 나면: 오류 메시지를 그대로 Claude Code에 붙여넣고 "firebase-config.js의 projectId 프로젝트에 연결해 줘"라고 요청한다.
  - 색인 배포 중 "콘솔에만 있는 색인을 지울까요?" 같은 질문이 나오면: 아니요(N)를 고른다. 원문 질문(firebase-tools 소스): "The following indexes are defined in your project but are not present in your firestore indexes file … Would you like to delete these indexes? Selecting no will continue the rest of the deployment."
- 노트: (4분, 실습 4) **사전 로그인 안내 권장**: 첫 `firebase login`(브라우저 인증 + CLI 질문)이 4분 안에 끝나기 빠듯하므로, 사전 안내문과 슬라이드 3 준비물에 "터미널에서 `firebase login` 완료"를 넣고, 못 한 사람은 휴식 시간(슬라이드 26)에 하게 한다. 시간(4분)은 그대로 둔다. Firebase CLI = 터미널에서 Firebase에 올리는 배달 도구(교무실 택배 접수대). 참고 명령(Claude Code가 실행할 것): `firebase use <프로젝트ID>`, `firebase deploy --only firestore`(규칙+색인), `firebase deploy --only hosting` `[확인필요: CLI 명령과 옵션 최신성]`. Firebase CLI 설치는 사전 준비 `[확인필요: 최신 설치 명령]`. 색인 파일은 모듈 3에서 오류 링크로 색인을 이미 만든 참가자에게는 없어도 동작한다. ignore 항목(규칙·색인·firebase.json·README.md·samples·functions·숨김 파일)은 이 파일들이 공개 주소로 내려받아지지 않게 하려는 것이다(functions는 심화 과제 뒤 다시 배포할 때 함수 소스가 올라가는 것을 막는다). 첫 배포에서 CLI 로그인 대기가 길어질 수 있으니 조교가 순회한다. 규칙 배포 전에는 앱이 잠깐 안 될 수 있다고 미리 말한다. 공개 주소는 다음 장 검증과 마지막 설문에서 쓰므로 메모장에 복사해 두게 한다.

## [슬라이드 50] 막히는지 직접 눈으로 확인하기
- 유형: 실습
- 본문:
  - 강사가 준 규칙 점검 페이지(`rules-check.html`)를 공개 주소 뒤에 붙여 연다.
  - 테스트 학생 계정으로 로그인하고 버튼을 하나씩 누른다. 막힘 6개, 열림 2개가 나와야 성공이다.
  - 안 막히면 규칙이 틀린 것이다. 슬라이드 48로 돌아간다.
  - 준비(미리, 슬라이드 49~50 사이 또는 휴식에): 교사 역할은 수업 2개(A, B)를 만든다. 학생 역할은 B에만 가입하고 B의 학습지 1개를 제출한다. 점검 페이지 입력칸 ①에 A, ②에 B의 수업코드를 넣는다(③ 다른 학생 uid는 선택).
- 도식: 점검 페이지 버튼 표. 열은 "버튼 / 시도 / 기대 결과 / 원칙 / 확인(O/X)".
  1. 버튼 1 / 가입하지 않은 수업(코드 입력)의 자료 목록 읽기 / 막힘 / 원칙 1
  2. 버튼 2 / 내 수업 학습지의 제출물 목록 읽기, 다른 학생 uid의 제출물 읽기 / 막힘 / 원칙 2
