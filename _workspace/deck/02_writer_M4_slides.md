# 02. 슬라이드 원고: M4 하네스 입문 (하네스 설치 · 말로 팀 만들기 · 실행) (슬라이드 20–25)

## 검수 반영 (이전 검수 결과 중 현재 슬라이드에 남은 것)
- 슬라이드 21(옛 23): 실험 플래그 단계와 settings.json file-box, 환경변수 설명 삭제. 폴더 만들기·`claude` 실행 확인만 남김. 에이전트 팀은 노트 한 줄(오늘은 사용하지 않음)로만 남김.
- 슬라이드 22(옛 24): 설치 범위 선택 패널 안내를 막힐 때·노트에 둠. 마켓플레이스 이름과 설치 명령은 저장소 기준으로 확인됨.
- 슬라이드 23(옛 25): 플랜 모드 진입은 `⏸ plan mode on`(Auto 시작 시 Shift+Tab 세 번, 또는 `/plan`). 승인 선택지 세 가지 중 "Yes, manually approve edits"를 고른다.
- 슬라이드 24(옛 26): `/agents` 대신 `.claude/agents/` 폴더를 열어 에이전트 파일을 확인한다.
- 복구 지점 안내 삭제.
- (하네스 활용 중심 개편, 2026-10-11) 원리 설명을 줄였다. 옛 20(M3, 혼자와 대화에서 팀 설계로)·21(혼자 맡기면 생기는 두 가지 문제)·22(하네스 정의)를 슬라이드 20 한 장으로 합쳤고, 7층·네 고리 도식은 삭제했다. 옛 27(세 기둥)과 28(정리)은 슬라이드 25 한 장으로 합쳤고 세 기둥 독립 슬라이드와 오케스트레이터 통신 규칙 설명은 삭제했다.

## 가정
- 슬라이드 20–25(6장), 권장 21분. 분 배분: 20(2) 21(2) 22(5) 23(5) 24(5) 25(2) = 21분. 설명 = 20, 25 (4분) / 실습 = 21–24 (17분). 옛 M3+M4 40분(M3 19분 + M4 21분)을 유지하며, 줄어든 설명 시간은 설치·실습(22–24)에 배분했다.
- 학습 목표: 하네스가 무엇인지 말하고, 플러그인을 설치해 말로 "생성+검수" 팀을 만들고 실행할 수 있다.
- 실습 산출물: `mini-harness/.claude/` (생성 에이전트 + 검수 에이전트 + 형식 스킬). 이 파일을 M5에서 열어 보고 말로 고친다.
- 실습 폴더 이름 `mini-harness`는 원본 그대로.
- `[확인필요]` 대상: 없음(이전 검수에서 확인 완료).
- 앱 제작 프롬프트는 없다. 예시 소재는 퀴즈 문항(수업 자료)이다.

## [슬라이드 20] 하네스가 해 주는 일
- 유형: 개념
- 본문:
  - 혼자 맡기면: 자기 실수를 스스로 알아채기 어렵고, 모호한 요청을 스스로 해석해 끝까지 실행해 버린다
  - 하네스 = 모델 바깥에서 도구·지침·검증·제어 흐름을 구성한 실행 환경
  - `revfactory/harness` = 말로 요청하면 역할이 나뉜 팀 파일을 만들어 주는 플러그인
  - 오늘 얻을 것: ① 플러그인 설치 ② 말로 팀 만들기 ③ 팀을 실행하고 검수 결과 보기
- 도식: 가로 3칸 화살표 "말로 요청 → 하네스가 팀 파일 생성 → 팀 실행·검수". 칸 1에 말풍선 한 줄(예: "형성평가 문항을 만들고 검수하는 하네스를 구성해줘"), 칸 2에 `.claude/` 폴더 아이콘, 칸 3에 "만드는 쪽 / 검수하는 쪽" 두 상자. 아래에 작은 단서 배지 "수치 49.5 → 79.3: 저자 자체 실험, 재현 검증 전"은 노트에만 두고 슬라이드에는 넣지 않는다.
- 프롬프트: (없음)
- 예상 결과: (없음)
- 막힐 때: (없음)
- 노트: 여기까지는 Claude Code 혼자와 대화하는 법이었다고 전환한다. 혼자 맡기면 생기는 문제는 한 줄만 말한다. 코드를 쓴 바로 그 에이전트가 검토하면 놓친 부분을 또 놓치기 쉽고, "정리해줘" 같은 모호한 요청을 스스로 해석해 필요한 데이터까지 지우는 사고가 보고된 바 있다(원본 표현). 하네스 정의는 《하네스 엔지니어링 with 클로드 코드》(황민호, 한빛미디어) 인용이다: "모델의 가중치를 건드리지 않고, 모델 바깥에 권한·도구·검증·관측을 설계해 에이전트가 홀로 움직이게 만드는 환경." 하네스는 새 AI 모델이 아니라 기존 모델이 동작하는 조건(도구·지침·검증·제어 흐름)을 바꾸는 환경이다. 저자 주장 "모델이 아니라 하네스가 결과를 결정한다"와 평균 점수 49.5 → 79.3은 저자가 직접 한 소프트웨어 엔지니어링 과제 15개 실험이고 관련 저장소 README에도 제3자 재현 검증이 아직 없다고 적혀 있다. 방향성만 참고하고 개선폭은 하나의 사례로 말한다(단서 배지: 저자 자체 실험, 재현 검증 전). 이 연수는 하네스의 원리를 설계하는 시간이 아니라 `revfactory/harness`를 써서 팀 파일을 만들게 하고 고치는 시간이라고 분명히 안내한다. 구성 요소 이름(에이전트·스킬·오케스트레이터)은 슬라이드 25에서 한 줄씩만 정리한다. (2분)

## [슬라이드 21] 실습: 플러그인 설치 전 준비 (새 폴더에서 시작)
- 유형: 실습
- 본문:
  - 새 폴더 `mini-harness`에서 Claude Code를 연다
  - 이 연수의 플러그인은 별도 설정(실험 플래그 등) 없이 바로 쓸 수 있다
  - 확인: 폴더 이름과 `claude` 실행 상태만 점검하고 다음 슬라이드로
- 도식: 2단계 `.flow` (폴더 만들기 → `claude` 실행 확인). 오른쪽에 작은 체크박스 "설정 파일 만지지 않기".
- 프롬프트:
  터미널에서:
  ```
  mkdir mini-harness && cd mini-harness
  claude
  ```
- 예상 결과: Claude Code 입력창이 열리고, 현재 폴더가 `mini-harness`로 보인다.
- 막힐 때:
  - `mkdir`가 안 되거나 폴더 위치를 모르겠다 → 지난 실습 폴더(`claude-training`) 바로 아래에 만들어도 된다. 이미 `mini-harness`가 있으면 그 폴더로 `cd`만 한다.
- 노트: `revfactory/harness` v2는 실험 플래그가 필요 없고, 플래그를 켜 두면 슬라이드 24의 quiz-writer/quiz-checker가 서브에이전트가 아니라 팀원(teammate)으로 실행되어 예시 화면과 달라질 수 있다. 그래서 이 연수에서는 어떤 플래그도 켜지 않는다. 강사용 한 줄: "에이전트 팀"은 별도의 실험 기능이며(플래그 이름 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`는 확인됨) 오늘은 사용하지 않는다. 대화형 세션에서만 동작하고 헤드리스(`-p`)에서는 팀원이 생성되지 않는다. 막힌 참가자는 짝 화면을 함께 보게 한다. (2분)

## [슬라이드 22] 실습: 플러그인 설치 (설치 통로 열고 설치하기)
- 유형: 실습
- 본문:
  - 저장소를 "마켓플레이스"로 등록한다
  - 그 안의 `harness`를 설치한다
  - `/plugin`에서 `harness`가 enabled면 성공
  - 주의: 커뮤니티가 만든 서드파티. 학교 관리 PC는 담당 부서와 먼저 상의
- 도식: 2줄 명령 + 아래에 `/plugin` 패널 캡처 자리 표시("harness: enabled").
- 프롬프트:
  Claude Code 입력창에서:
  ```
  /plugin marketplace add revfactory/harness
  /plugin install harness@harness-marketplace
  ```
  확인: `/plugin`
- 예상 결과: `/plugin` 패널 목록에 `harness`가 보이고 활성화(enabled) 상태.
- 막힐 때:
  - 설치 명령이 인식되지 않는다 → 마켓플레이스 이름이 다를 수 있다. `/plugin` 패널에서 등록된 마켓플레이스 이름을 보고 `harness@<그 이름>`으로 바꾼다.
  - 학교 PC라서 설치가 막힌다 → 짝 화면을 함께 본다.
  - `/plugin install`을 입력했더니 바로 설치되지 않고 패널이 열린다 → 정상이다. 패널에서 설치 범위를 고르고 설치한다.
- 노트: 세션 안에서 `/plugin install`을 입력하면 설치 범위를 고르는 패널이 열린다(이 패널을 따라가는 시간 때문에 5분). 플러그인 저장소를 "마켓플레이스"로 등록하는 것이 첫 줄, 그 안의 플러그인을 설치하는 것이 둘째 줄이다. 마켓플레이스는 플러그인 카탈로그 저장소이므로, 저장소를 먼저 등록하고 그 안의 플러그인을 설치한다. `revfactory/harness`는 Anthropic이 아니라 개인 개발자가 공개한 오픈소스이고, 플러그인 안의 스킬 문구는 Claude Code가 내 권한으로 실행하므로 낯선 저장소는 설치 전에 코드를 훑어보는 습관이 안전하다. 학교 공용 계정이나 관리 PC에서는 설치 전에 담당 부서와 상의한다(원본 문장 유지). 마켓플레이스 이름 `harness-marketplace`와 두 줄 설치 명령은 검수에서 저장소 기준으로 확인됨. (5분)

## [슬라이드 23] 실습: 말로 팀 만들기 (플랜 모드)
- 유형: 실습
- 본문:
  - 플랜 모드로 어떤 파일이 만들어질지 먼저 확인: Shift+Tab을 눌러 `⏸ plan mode on`이 보이게 한다(Auto로 시작했다면 세 번). 또는 프롬프트 앞에 `/plan`
  - 계획이 나오면 선택지에서 **"Yes, manually approve edits"** 를 고른다 ("Yes, and use auto mode"는 고르지 않는다)
  - 하고 싶은 말을 그냥 문장으로 설명한다
  - 만드는 에이전트 1 + 검수 에이전트 1 (검수는 읽기만)
- 도식: 입력 문장 → 플랜 모드 계획 확인 → 승인(Yes, manually approve edits) → `.claude/` 폴더 생성. 계획 확인 단계에 "읽기 전용 계획 확인" 표식.
- 프롬프트:
  ```
  형성평가 문항을 만들고 검수하는 하네스를 구성해줘. 주제를 입력하면
  객관식 퀴즈를 생성하는 에이전트 하나와, 생성된 문항의 정답·오탈자만
  검수하는 에이전트 하나로 구성해줘. 검수 에이전트는 파일을 수정하지
  않고 읽기만 하게 해줘
  ```
- 예상 결과: 아래와 비슷한 파일 구조(실행마다 파일 이름과 문구가 조금씩 다르다. 예시 중 하나).
  file-box "생성된 폴더 구조 (예시)"
  ```
  mini-harness/
  └── .claude/
      ├── agents/
      │   ├── quiz-writer.md      ← 퀴즈 생성 담당
      │   └── quiz-checker.md      ← 검수 담당 (Read만 허용)
      └── skills/
          └── quiz-format/
              └── SKILL.md          ← 문항 형식 절차서
  ```
- 막힐 때:
  - 플러그인이 반응하지 않고 일반 답변만 한다 → 문장 맨 앞이 "하네스를 구성해줘"로 읽히도록 위 문장을 그대로 붙여 넣는다.
  - 파일 이름이 나와 다르다 → 정상이다. 에이전트 2개와 스킬 1개가 있으면 된다.
  - 계획 승인 화면의 선택지가 다르게 보인다 → 최신 버전은 "Yes, and use auto mode / Yes, manually approve edits / No, keep planning" 세 가지다. 두 번째를 고른다.
- 노트: 이 플러그인은 `/quiz`처럼 정해진 커맨드가 아니라, 문장이 "팀을 구성해 달라"는 요청임을 Claude가 스스로 알아보고 스킬을 실행한다. 처음에는 여러 파일을 한꺼번에 만들므로 플랜 모드(M2에서 배운 Shift+Tab)로 계획을 확인하고 승인하는 습관을 들인다(파일 수정 전 계획 확인). 생성된 `quiz-checker.md`를 열어 보면 `name`, `description`, `tools: Read`, "하지 않는 일"이 이미 들어 있다. 파일 내용은 플러그인이 대신 써 준 것이고, M5에서 열어 보고 말로 고친다고 예고한다. 최신 Claude Code는 Auto 모드로 시작할 수 있고, 계획 승인 화면의 선택지는 "Yes, and use auto mode / Yes, manually approve edits / No, keep planning"이다. 첫 번째를 고르면 세션이 Auto 모드(분류 모델이 대신 검토)로 바뀌므로 연수에서는 "manually approve edits"를 고르게 한다. 상태 표시줄 문구 `⏸ plan mode on`은 확인됨. 새로 만들어진 `.claude` 폴더를 Claude Code가 인식하지 못하면 `/exit` 후 `claude`로 다시 시작한다(세션 시작 때 없던 agents/skills 폴더는 재시작이 필요할 수 있다). (5분)

## [슬라이드 24] 실습: 팀 실행하고 검수 결과 보기
- 유형: 실습
- 본문:
  - 만드는 에이전트와 검수 에이전트가 따로 일한다
  - 검수 에이전트가 문항의 문제를 지적하는지 확인한다
- 도식: quiz-writer(문항 생성) → quiz-checker(별도 컨텍스트, 읽기만) → 지적 사항, 화살표 흐름. checker 칸에 "다른 눈" 라벨.
- 프롬프트:
  ```
  이진 탐색 개념으로 객관식 퀴즈 3문항을 만들고 검수까지 맡겨줘
  ```
- 예상 결과: 예시 터미널(내용은 실행마다 다름)
  ```
  quiz-writer가 문항을 생성했습니다. quiz-checker를 호출합니다…
  [quiz-checker] 2번 문항: 보기 ③과 ④가 모두 조건을 만족해 정답이
  두 개로 해석될 수 있습니다. 보기 수정을 권장합니다.
  ```
- 막힐 때:
  - 검수 에이전트가 호출되지 않는다 → 프롬프트 끝의 "검수까지 맡겨줘"를 빼먹지 않았는지 확인하고 다시 보낸다. 안 되면 `.claude/agents/` 폴더에 두 파일(quiz-writer, quiz-checker)이 있는지 확인한다.
  - 지적 사항이 없다고 나온다 → 정상일 수 있다. 주제를 "이진 탐색 vs 선형 탐색"처럼 헷갈리기 쉬운 것으로 바꿔 다시 요청해 본다.
- 노트: 주제는 담당 과목에 맞게 바꿔도 된다. 핵심은 "만드는 역할과 검수하는 역할이 서로 다른 컨텍스트에서 실행됐다"는 점을 눈으로 확인하는 것이다. 지적 내용은 예시이고 실제 출력과 달라도 괜찮다. 시간이 남는 참가자는 내용 확인 후 "내가 보기엔 이 지적이 맞나?"를 직접 판단해 본다(사람의 눈도 최종 검수). 끝나면 손 들기: "검수 에이전트의 지적이 나온 분?" `/agents`는 최신 버전에서 목록을 보여 주지 않고 관리 안내만 출력하므로(예전 버전은 목록·생성 화면) 에이전트 확인은 폴더 열기로 한다. (5분)
