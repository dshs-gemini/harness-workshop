# 02. 슬라이드 원고 M7 종합 프로젝트: 우리 교과 단원 수업 패키지 만들기 (슬라이드 56–67, 50분)

## 가정
- 근거: 공통 브리프(revfactory/harness 활용 중심 개편, 2026-10-11)의 'M7 상세 설계'와 사용자 확정(M7은 단원 명세를 쓴 뒤 하네스에게 팀 구성을 요청, 설계도 5항목·`.claude` 파일 직접 만들기 없음). 번호 53–64, 12장(58번은 '터미널 로그인' 개념 슬라이드).
- 이 연수는 에이전트·스킬·오케스트레이터의 원리를 가르치지 않는다. M7에서는 하네스(revfactory/harness)가 만든 팀을 확인하고 실행하는 데 집중한다. 구성 요소 이름은 처음 나올 때 한 줄 정의만 한다.
- 하네스 플러그인은 M4(22번)에서 설치했다고 가정한다. 미설치자는 55번 막힐 때에서 M4 22번(플러그인 설치)으로 안내한다.
- 하네스가 만드는 에이전트·스킬의 개수와 이름은 하네스가 정한다. 슬라이드는 개수·이름을 지정하지 않고 "생성된 팀"이라고만 쓴다.
- 실습 목적: "Firebase 사용하기 설정만 사람이 하면 나머지는 하네스와 Claude Code가 한다"를 체험한다. 최종 목표는 Firebase Hosting 배포 주소(`https://프로젝트ID.web.app` 형태)를 브라우저로 열어 확인하고 짝에게 전하는 것이다.
- 사람이 하는 일: M6에서 이미 한 콘솔 설정(테스트 프로젝트, 웹 앱 등록, Google 로그인 켜기, Firestore 만들기)의 완료 확인, 승인(① `firebase login` 브라우저 로그인 ② 계획·명령 승인)뿐이다. M7은 새 콘솔 작업을 요구하지 않는다. 예외로 61번 막힐 때에서 `auth/unauthorized-domain` 오류가 날 때만 승인된 도메인 추가를 안내한다.
- Claude Code가 하는 일: 웹앱 코드, Firebase 연결 값 가져오기(`firebase apps:sdkconfig`), `firestore.rules` 작성, Hosting 설정, 배포, 주소 안내. 연결 값 가져오기가 안 되면 프로젝트 ID만 알려 주면 된다.
- 앞 모듈 연계: M4(20–25)의 하네스 설치·팀 구성 요청, M6(34–52)의 테스트 프로젝트·웹 앱 등록·Google 로그인·Firestore(프로덕션 모드)를 이미 마쳤다고 가정한다. M6를 마치지 못한 참가자는 60번 막힐 때에 되돌아갈 슬라이드 번호를 적었다.
- M6 슬라이드 번호 참조(새 번호): 테스트 프로젝트 만들기 35, 웹 앱 등록 36, Google 로그인 설정 38, Firestore 만들기 40, 요금제(Spark/Blaze) 41, 마지막 슬라이드 52. M6 원고가 아직 옛 번호일 수 있어 조립 때 일치 여부를 확인한다.
- 예시 단원은 하나로 고정했다: 정보 교과 "알고리즘 — 탐색"(단원 코드 `info-search-01`). 교육과정 성취기준 문장, 학년, 출처는 지어내지 않고 `[교사 입력]`으로 두었다. 다른 교과로 바꾸는 방법은 54번 본문 한 줄.
- 보안: 한 문장으로만 다룬다. Claude Code가 `firestore.rules`(로그인한 본인 uid 문서만 읽기·쓰기)를 함께 만들어 배포하고, 배포 전 플랜 모드 계획에서 "무엇을 배포하는지"를 한국어로 설명하게 한다. 교사용 정답은 웹앱 파일에 넣지 않는다(페이지 소스로 보인다). 개인정보·비밀 키는 넣지 않는다.
- 문항은 로그인 없이 보이고, 로그인은 답 저장·불러오기에만 쓴다(짝이 주소를 열어 로그인 없이 문항을 볼 수 있다).
- Firebase SDK 버전 번호, 파일 구조, Firestore 문서 경로는 슬라이드에서 지정하지 않는다. Claude Code가 정한다.
- localhost, 로컬 서버, 승인된 도메인 사전 추가는 요구하지 않는다.
- M6에서 요금제를 Blaze로 올렸더라도 M7 프로젝트는 Authentication·Firestore·Hosting만 쓴다. Storage와 Cloud Functions는 쓰지 않는다. Node.js·Firebase CLI·`firebase login`은 M6 47에서 함께 해 두었을 수 있으며, 59번에서는 연결 확인만 한다.
- 정답 표시·채점·교사용 열람 화면은 만들지 않는다(교사는 콘솔 Firestore 데이터 화면에서 확인, 열람 화면은 선택 심화). 워크북은 학생 응답 저장·재방문 불러오기까지다.
- 용어: 테스트 계정 = Firebase 실습에 쓰는 개인 구글 계정(학생·업무 계정이 아닌 것).
- 도식은 53(흐름 5단계 + 폴더 트리 + 안전 원칙)과 63(회고 한 장)에만 쓴다. 58은 도식 없이 단계·명령 중심이다. 나머지 슬라이드는 `도식` 줄 없이 구성했다.
- 분 합계 검산: 53(2) + 54(5) + 55(5) + 56(7) + 57(3) + 58(2) + 59(4) + 60(8) + 61(4) + 62(5) + 63(3) + 64(2) = **50분**. 설명 4분(53, 58) / 나머지 46분. 4 + 46 = 50. (58번 개념 슬라이드를 새로 끼우면서 53을 3→2분, 59(옛 58)를 5→4분으로 줄여 M7 50분·총 180분을 유지했다. 앞선 증감: M6 8분 삭제분을 M7에 더해 54 +1, 56 +1, 옛 58 +2, 옛 59 +2, 옛 60 +1, 옛 61 +1.)
- `[확인필요]` 유지: 하네스가 생성한 스킬이 `/` 목록에 보이는지와 스킬 이름, 단계 분할 요청("슬라이드까지만")이 실제로 동작하는지(리허설 1회 필수), 새 폴더에서 하네스 플러그인이 보이는지(설치 범위), `firebase apps:sdkconfig` 동작, Node.js 필요 여부, `firebase login --no-localhost` 동작, 신규 프로젝트의 기본 Hosting 사이트 생성 방식, Hosting 기본 주소가 승인된 도메인에 기본 포함인지, 콘솔 프로젝트 ID 위치의 한국어 UI 이름.

## [슬라이드 56] 오늘의 프로젝트: 우리 교과 단원 수업 패키지
- 유형: 개념
- 본문:
  - 내 교과의 한 단원으로 **수업 슬라이드(`slides.html`)와 학생 워크북 웹앱**을 만들고, **Firebase Hosting 배포 주소**로 확인하는 것이 최종 목표다.
  - 사람은 단원 명세 작성, Firebase 설정(M6에서 완료), 승인만 한다. 팀 구성은 하네스가, 코드·규칙·배포는 Claude Code가 한다.
  - 흐름: 단원 명세 → 하네스 구성 → 수업 슬라이드 → 워크북 배포 → 점검·공유. 개인 작업, 마지막에 짝과 바꿔 점검한다.
  - 하네스 = 작업을 설명하면 역할이 나뉜 팀(`.claude/agents/`, `.claude/skills/` 파일)을 만들어 주는 플러그인(revfactory/harness, M4에서 설치).
  - 지켜야 할 것: 테스트 계정만 쓴다 · 학생 실제 정보는 넣지 않는다 · 교과 내용의 정확성은 교사가 책임진다.
  - 테스트 계정 = Firebase 실습에 쓰는 개인 구글 계정(학생·업무 계정이 아닌 것).
- 도식: 가로 흐름 5단계 칸. 왼쪽부터 ① 단원 명세(`unit-spec.md`, 사람이 씀) ② 하네스 구성(팀 생성, 사람이 계획 승인) ③ 수업 슬라이드(`slides.html`) ④ 워크북 배포(`workbook/` + 규칙 + 배포 주소) ⑤ 점검·공유(사람이 확인, 짝 점검, 배포 주소 전달). 칸 아래에 슬라이드 번호 범위: ① 57 ② 58 ③ 59–60 ④ 61–65 ⑤ 66–67. 오른쪽 아래에 작업 폴더 트리 `unit-project/` 아래 `unit-spec.md`(내가 씀), `.claude/agents/`·`.claude/skills/`(하네스가 생성), `slides.html`, `workbook/`, `firestore.rules`, `firebase.json`(Claude Code가 생성). 맨 아래에 안전 원칙 3개 라벨(테스트 계정만 · 실제 학생 정보 없음 · 교과 내용은 교사 확인).
- 노트: "오늘은 앞 모듈에서 배운 것을 하나의 산출물로 묶습니다." 만드는 것은 두 가지다. 하나는 수업에서 넘겨 가며 쓰는 슬라이드 파일, 다른 하나는 학생이 구글 계정으로 로그인해 답을 저장하는 워크북 웹앱이다. 최종 목표는 웹앱을 Firebase Hosting으로 배포하고 주소를 브라우저로 여는 것이다. 순서는 다섯 단계다. 먼저 교사가 단원 명세를 쓰고, 그 명세로 하네스에게 팀 구성을 요청한다. 하네스는 M4에서 설치한 플러그인이고, 오늘은 팀의 내부 구조를 설계하지 않는다. 팀이 만들어지면 슬라이드, 워크북 배포, 점검 순서로 진행한다. 핵심 체험은 하나다. Firebase 설정은 M6에서 이미 했고, 오늘은 로그인 승인과 계획·명령 승인만 하면 나머지는 하네스와 Claude Code가 한다. 규칙 세 가지를 먼저 말한다. 첫째, 테스트용 구글 계정만 쓴다. 둘째, 실제 학생 이름·이메일·응답은 넣지 않는다. 셋째, Claude Code가 쓴 교과 내용은 틀릴 수 있으므로 최종 확인은 교사가 한다. 이 프로젝트는 개인별이고, 짝은 66번에서 서로 바꿔 점검할 때 만난다. 교과는 정보가 아니어도 된다. 예시 단원은 정보 교과의 "알고리즘 — 탐색" 하나로 계속 쓴다. (2분)

## [슬라이드 57] 단원 명세 쓰기: unit-spec.md
- 유형: 실습
- 본문:
  - 새 폴더 `unit-project`에서 `claude`를 시작하고, Claude Code가 **빈 항목마다 질문만** 하게 한다. 내용은 교사가 쓴다.
  - 항목: 단원 코드 · 교과·학년·단원명 · 성취기준(교육과정 문서에서 복사) · 학습 목표 2~3 · 핵심 개념 3~5 · 워크북 문항 5~8(객관식·단답·서술) · 출처.
  - 이 명세 한 장이 다음 단계에서 하네스가 읽는 입력이다.
  - 예시: 정보 교과 "알고리즘 — 탐색". 내 교과로 바꾸려면 교과·단원명·성취기준·핵심 개념·문항만 바꾼다.
- 프롬프트: (먼저 `/exit` → `cd ..` → `mkdir unit-project` → `cd unit-project` → `claude`로 claude-training 밖의 새 폴더에서 시작한 뒤 붙여 넣는다.)
  ```
  unit-spec.md 파일을 만들어줘. 항목은 다음과 같다: 단원 코드(영문 소문자·숫자·하이픈), 교과·학년·단원명, 성취기준(내가 붙여 넣는 문장 그대로), 학습 목표 2~3개, 핵심 개념 3~5개, 워크북 문항 5~8개(객관식·단답·서술을 섞고, 문항마다 id·유형·질문·교사용 정답), 출처.
  파일에는 항목 제목만 쓰고 내용은 비워 둬. 그다음 비어 있는 항목을 한 번에 하나씩 나에게 질문해줘.
  내가 답한 문장은 그대로 기록하고, 내용을 새로 지어내거나 고치지 마. 내가 모른다고 하면 "확인 필요"라고 적어 둬.
  ```

  - 문항이 5개에 못 미침 → 지금은 5개면 충분하다. 나머지는 연수 후에 `unit-spec.md`에 더한다.
  - 5분 안에 못 끝냄 → 예시 file-box를 그대로 `unit-spec.md`로 저장해 달라고 요청하고 진행한다(내 교과 내용은 연수 후 바꾼다).
- 노트: "여기서부터 5분은 교사가 쓰는 시간입니다." Claude Code는 질문하고 기록하는 역할이다. 내용을 쓰는 사람은 교사다. 이유는 두 가지다. 교과 내용의 정확성을 교사가 책임져야 하고, 이 명세가 다음 단계에서 하네스가 만든 팀이 읽는 유일한 입력이기 때문이다. 명세에 없는 사실은 팀이 근거 없이 채우게 되므로 비워 둘 항목은 "확인 필요"로 남긴다. 성취기준은 요약하지 않고 교육과정 문서에서 그대로 복사해 붙인다. 시간이 없으면 학습 목표 2개, 핵심 개념 3개, 문항 5개로 줄인다. claude-training 밖(`cd ..`)에 새 폴더를 만드는 이유: 이 폴더에 하네스가 `.claude/`를 새로 만들므로, 상위 폴더의 CLAUDE.md와 M4·M5에서 만든 팀이 섞이지 않게 한다. (5분)

## [슬라이드 58] 하네스에게 팀 구성 요청하기
- 유형: 실습
- 본문:
  - `unit-project`의 같은 세션에서, 단원 명세로 **하네스에게 팀 구성을 요청**한다. 하네스는 M4(25번)에서 설치했다.
  - 순서: ① 플랜 모드로 바꾸고(`⏸ plan mode on`이 보일 때까지 Shift+Tab, 또는 붙여 넣을 내용 맨 앞에 `/plan `) 아래 프롬프트를 붙여 넣는다. ② 계획을 읽고 **"Yes, manually approve edits"**로 승인한다. ③ 만들어진 팀 목록을 확인한다. ④ **`/exit` → `claude`로 다시 시작**한다.
  - 하네스가 만드는 것: 에이전트(역할이 정해진 하위 작업자, `.claude/agents/*.md`), 스킬(재사용 절차, `.claude/skills/*/SKILL.md`), 오케스트레이터(팀 실행 순서를 정한 스킬). 개수와 이름은 하네스가 정한다.

  - 이 단계에서는 슬라이드와 앱 코드를 만들지 않는다. 팀만 만든다.
- 프롬프트:
  ```
  하네스를 구성해줘.
  단원 명세는 unit-spec.md야. 만들 것은 ① 수업용 슬라이드 slides.html ② 학생 워크북 웹앱(Firebase Hosting에 배포) ③ 교과 내용 검수야.
  지금은 팀 구성만 하고 slides.html과 앱 코드는 만들지 마.
  학생 개인정보와 비밀 키는 다루지 말고, 교사용 정답은 웹앱에 넣지 마.
  도구 설치와 명령 실행은 실행 전에 물어봐.
  ```
- 예상 결과: 플랜 모드가 만들 팀(에이전트와 스킬 목록)을 먼저 보여 준다. 이어서 승인 화면에 세 선택지가 뜬다: "Yes, and use auto mode" / "Yes, manually approve edits" / "No, keep planning". **"Yes, manually approve edits"**를 고른다(첫째를 고르면 세션이 Auto 모드로 바뀌어 파일이 확인 없이 만들어진다). 첫째 선택지가 "Yes, auto-accept edits"로 보일 수도 있다. 승인 뒤 파일마다 승인 창이 뜨면 내용을 보고 Yes를 고른다. 아래는 생성 결과의 한 예다. 이름과 개수는 실행마다 다르다.
  ```
  [file-box] unit-project/.claude (생성된 팀의 예)
  .claude/agents/   에이전트 파일 (예: 슬라이드 담당, 워크북 담당, 검수 담당)
  .claude/skills/   스킬 파일 (예: 팀 실행 순서를 정한 오케스트레이터)
  ```
  확인 방법: `! ls .claude/agents .claude/skills`로 목록을 보거나 "만들어진 에이전트와 스킬의 이름과 역할을 한 줄씩 알려줘"라고 요청한다. 확인한 뒤 `/exit` → `claude`로 다시 시작한다. 다시 시작한 세션에서 `/` 목록에 새 스킬이 보이면 성공이다 `[확인필요: 스킬 이름은 하네스가 정함]`.
- 막힐 때:
  - 하네스가 인식되지 않음(플러그인 없음) → M4 25번(플러그인 설치)을 따른다. `/plugin` 화면에서 설치 목록에 harness가 있는지 본다 `[확인필요: 설치 범위에 따라 새 폴더에서 보이는지]`.
  - 계획에 `slides.html`, `workbook/` 같은 앱 파일이 올라옴 → 거부하고 "팀 구성 파일만 만들어줘"를 다시 요청한다.
  - 계획에 개인정보 수집 항목이나 외부 AI 키 사용이 보임 → 승인하지 말고 "그 항목은 빼줘"라고 요청한다.
  - 다시 시작했는데도 스킬이 `/` 목록에 안 뜸 → `! ls .claude/skills`로 파일이 있는지 확인하고, 있으면 `/reload-skills`를 입력해 본다 `[확인필요]`. 파일이 없으면 하네스 구성을 다시 요청한다.
  - 5분 안에 끝나지 않음 → 팀 생성이 끝날 때까지 승인 창만 처리하고, 확인과 재시작은 59번 시작 전에 한다.
- 노트: 오늘의 핵심 요청은 "하네스를 구성해줘" 한 문장과 작업 설명이다. M4에서 퀴즈 팀을 만든 방식과 같다. 하네스는 설명을 읽고 계획을 세운 뒤 팀 파일을 만든다. 플랜 모드 승인은 M2에서 계획을 확인하고 승인한 절차와 같다. Auto 모드로 시작했다면 Shift+Tab을 세 번 눌러야 plan에 닿을 수 있어, 붙여 넣을 내용 맨 앞에 `/plan `을 붙이는 편이 쉽다. 계획에서 사람이 볼 것은 세 가지다. 만들 팀이 ①②③ 작업(슬라이드, 워크북 배포, 검수)을 모두 맡는가, 개인정보·비밀 키·교사용 정답 금지가 반영되었는가, 앱 파일을 아직 만들지 않는가. 팀 파일의 세부 내용(도구 권한, 문구)은 오늘 모두 읽지 않는다. 구성 요소는 처음 나온 용어만 정의한다. 에이전트는 역할이 정해진 하위 작업자 파일, 스킬은 재사용 절차 파일, 오케스트레이터는 팀의 실행 순서를 정한 스킬이다. 재시작하는 이유: 새로 만든 `.claude/agents`, `.claude/skills` 폴더는 세션을 시작할 때 없었으므로, 다시 시작해야 인식된다(근거 https://code.claude.com/docs/en/sub-agents, https://code.claude.com/docs/en/skills). 파일 내용이 마음에 들지 않아도 지금 고치려 하지 않는다. 59번 실행 결과를 보고 말로 고친다. (5분)

## [슬라이드 59] 수업 슬라이드 만들기: 하네스 팀 실행 1단계

## [슬라이드 61] 터미널에서 한 번 로그인하면 Claude Code가 이어받는다
- 유형: 개념
- 본문: 터미널에서 한 번 로그인해 두면, 그 로그인으로 하던 명령을 Claude Code가 대신 실행합니다.
  Firebase: `firebase login` 한 번 → 프로젝트 조회, 연결 값 가져오기, 배포를 Claude Code가 합니다. (다음 슬라이드에서 실습)
  GitHub: `gh auth login` 한 번 → "저장소를 만들어 올려줘" 같은 요청을 Claude Code가 `gh` 명령으로 실행합니다. (오늘 실습에서는 쓰지 않습니다)
  자동으로 이어지는 것은 명령 실행입니다. 무엇을 실행할지는 내가 승인합니다.
- 도식: 가로 4칸 흐름. ① 내가 로그인(터미널에서 한 번만) → ② 컴퓨터에 저장(내 컴퓨터에 로그인 정보가 남음) → ③ Claude Code 실행(같은 로그인으로 명령 실행) → ④ 내가 승인(명령마다 허용 여부 선택). 사람이 하는 칸(①, ④)과 Claude Code가 하는 칸(③)을 색으로 구분한다. 아래에 두 줄 예시: Firebase `firebase login` → 배포, GitHub `gh auth login` → 저장소에 올리기.
- 노트: 한 문장으로 말해 준다: "터미널에서 한 번 로그인해 두면, 그 계정으로 하던 명령을 Claude Code가 대신 실행하므로 이후 작업이 이어진다. 단, 자동인 것은 실행이고 승인은 사람이 한다." 로그인은 사람이 직접 해야 하는 부분(브라우저에서 계정 선택·허용)이고, 그 뒤의 명령은 Claude Code가 터미널 명령으로 실행한다. 승인 화면은 권한 모드에 따라 달라지므로 "명령마다 승인"을 기본으로 안내하고, 승인 화면에서 배포·올리기(push) 같은 공개 행위 명령은 읽고 승인하게 한다. Firebase: 공식 Firebase 플러그인(Firebase MCP 서버)은 Firebase CLI와 같은 자격증명을 쓴다(근거 https://firebase.google.com/docs/cli/mcp-server). 그래서 `firebase login`을 한 번 해 두면 다음 슬라이드의 프로젝트 조회와 배포를 Claude Code가 이어서 한다. GitHub: 깃허브 CLI(`gh`)는 `gh auth login`으로 브라우저 로그인을 하면 토큰이 컴퓨터의 자격증명 저장소에 보관된다(근거 https://cli.github.com/manual/gh_auth_login). Claude Code 공식 문서는 "create a pr"처럼 요청하면 Claude가 `gh pr create`로 풀 리퀘스트를 만든다고 안내한다(근거 https://code.claude.com/docs/en/common-workflows). `gh`는 따로 설치해야 하므로 오늘은 설치를 안내하지 않고, 원리만 알려 준다. 주의 세 가지: ① 로그인한 계정으로 할 수 있는 일은 Claude Code도 할 수 있으므로 실습에는 연습용 프로젝트·저장소를 쓴다. ② 깃허브에 올리면 공개될 수 있으니 저장소는 비공개로 만들고 비밀 키·학생 정보는 올리지 않는다. ③ 학교 계정과 개인 계정을 섞어 로그인하지 않는다. 원본 대비 변경: 원본에 없는 설명으로, M7 Firebase 연결 실습을 이해하는 배경으로 새로 넣었다. (2분)

## [슬라이드 62] Firebase 연결: 미리 로그인해 두기
- 유형: 실습
- 본문:
  1. 브라우저에서 Firebase 콘솔(`console.firebase.google.com`)에 구글 계정으로 로그인하고, M6에서 만든 테스트 프로젝트가 보이는지 확인한다. 이 로그인은 계정 확인용이다.
  2. 터미널에서 `firebase login`을 실행하고, 열린 브라우저에서 같은 구글 계정을 골라 허용한다. 한 번만 하면 된다.
  3. 터미널에서 Firebase 플러그인을 설치한다. 이렇게 하면 Claude Code가 이 로그인을 이어받아 프로젝트 조회와 배포를 한다.
  4. Claude Code에서 "내 Firebase 프로젝트 목록을 보여줘"로 연결을 확인한다. 프로젝트 ID가 보이면 성공이다.
- 프롬프트: 일반 터미널에서 순서대로 실행한다(Claude Code 밖).
  ```
  firebase login
  firebase projects:list
  claude plugin marketplace add firebase/firebase-tools
  claude plugin install firebase@firebase
  ```
  그다음 Claude Code 입력창에서:
  ```
  내 Firebase 프로젝트 목록을 보여줘
  ```
- 예상 결과: `firebase projects:list`에 M6 테스트 프로젝트 ID가 표로 나오고, Claude Code도 같은 프로젝트 목록을 답한다. 이 연결이 끝나면 다음 슬라이드(63)에서 연결 값 가져오기, 규칙 작성, 배포를 Claude Code가 한다.
- 막힐 때:
  - `firebase` 명령이 없다고 나옴 → Node.js(20 이상)를 설치한 뒤 `npm install -g firebase-tools`를 실행한다. 학교 PC에서 설치가 막히면 Claude Code에 방법을 물어본다 `[확인필요: 학교 PC 설치 권한]`.
  - 브라우저가 안 열림 → `firebase login --no-localhost`를 실행하고 화면에 나온 안내대로 코드를 붙여 넣는다.
  - Docker 경로(M1 5~7번)로 시작함 → `firebase`는 이미지에 들어 있다. 로그인은 `docker compose run --rm claude firebase login --no-localhost`로 먼저 해 두면 보관되어 이 슬라이드에서는 확인만 하면 된다 `[확인필요: Windows 리허설]`.
  - 프로젝트 목록이 비어 있거나 권한 오류 → 콘솔에 로그인한 계정과 `firebase login`에서 허용한 계정이 같은지 확인한다. 다르면 `firebase logout` 후 다시 로그인한다.
  - 학교 관리 계정(Google Workspace)이 관리자 정책으로 막힘 → 개인 구글 계정(테스트 계정)으로 한다 `[확인필요: 공식 문서 근거 없음]`.
  - `claude plugin` 명령이 안 됨 → 수동 연결로 대신한다: `claude mcp add firebase npx -- -y firebase-tools@latest mcp`, 확인은 `claude mcp list`.
- 노트: 이 슬라이드의 목적은 "Firebase 쪽 설정은 사람이 한 번만 하고, 이후는 Claude Code가 이어받는다"를 체험하는 것이다. 콘솔(브라우저)에 로그인해 두는 것과 Firebase CLI 인증은 따로이며, 공식 문서에서 콘솔 로그인이 CLI 인증을 대신한다는 근거는 찾지 못했다. 그래서 `firebase login`을 한 번 실행해 같은 구글 계정으로 허용하고, 콘솔에 먼저 로그인해 두면 그 계정 선택이 쉽다는 정도로만 안내한다. 브라우저에서 계정 선택 화면이 어떻게 보이는지는 공식 문서에 설명이 없어 `[확인필요]`다. 공식 Firebase 플러그인(Firebase MCP 서버)은 Claude Code에서 프로젝트 조회, 연결 값 가져오기, 보안 규칙 검증, 배포 같은 도구를 쓰게 해 주고, Firebase CLI와 같은 자격증명을 쓴다(근거 https://firebase.google.com/docs/cli/mcp-server). Claude Code 안에서 `!`를 앞에 붙여 `! firebase login`처럼 실행하는 방법은 문서에 브라우저가 열리는 명령의 동작이 명시되어 있지 않으므로 연수에서는 일반 터미널을 쓴다 `[확인필요]`. 4분 중 1~2단계(콘솔 로그인 확인, `firebase login`)는 연수 전에 해 두면 더 여유 있다. 사람이 하는 일은 콘솔 로그인 확인, `firebase login` 허용, 이후 계획·명령 승인이고, 새 콘솔 작업은 없다. 배포는 공개 행위이므로 63번에서 계획을 읽고 승인한다. 보안은 한 문장: 63번에서 Claude Code가 로그인한 본인 uid 문서만 읽고 쓰는 `firestore.rules`를 함께 만들어 배포한다. 교사용 정답은 웹앱 파일에 넣지 않는다(페이지 소스로 보임). 이 구조는 Spark(무료)로 되고 Storage와 Cloud Functions(Blaze 필요)는 쓰지 않는다. 학생 응답은 콘솔 Firestore 데이터 화면에서 확인한다. (4분)

## [슬라이드 64] 배포 주소로 확인하기
- 유형: 실습
- 본문:
  - 새 탭에서 배포 주소(`https://프로젝트ID.web.app` 형태)를 연다.
  - 확인 5가지: ① 문항이 로그인 없이 보임 ② Google 로그인(테스트 계정) ③ 답 저장 ④ 새로고침 후 불러오기 ⑤ (선택) 콘솔 Firestore 데이터에서 저장된 문서 확인.
  - 확인이 끝나면 주소를 짝에게 전한다.
- 막힐 때:
  - 로그인 팝업에서 `auth/unauthorized-domain`이 뜸 → 오류 문구를 Claude Code에 그대로 보여 주면 콘솔 보안(Security) > Authentication > 설정(Settings) 탭 > 승인된 도메인(Authorized domains)에 어떤 도메인을 추가할지 알려 준다. 사람이 콘솔에서 그 도메인만 추가한다 `[확인필요: Hosting 기본 주소가 기본 포함인지]`.
  - 화면이 비어 있음/404 → 오류 문구나 화면을 그대로 Claude Code에 전달한다.
  - 저장 시 `Missing or insufficient permissions` → 오류 문구를 그대로 Claude Code에 전달한다.
- 노트: 4분 동안 배포된 결과를 직접 확인한다. 로그인 없이 문항이 보여야 짝이 주소만 열어서 볼 수 있다. 로그인은 저장과 불러오기에만 쓴다. ⑤는 시간이 남는 사람만 한다. 콘솔 Firestore 데이터 화면에서 응답이 저장된 문서를 볼 수 있다. 로그인 팝업 오류 `auth/unauthorized-domain`은 M6 41번에서 한 번 보았다. 승인된 도메인은 로그인 팝업을 허용하는 주소 목록이다. 2025-04-28 이후 만든 프로젝트는 기본 목록이 다를 수 있어, Hosting 기본 주소의 포함 여부는 오류가 날 때만 확인한다 `[확인필요]`. 오류가 나면 문구를 그대로 Claude Code에 전달하는 습관을 65번에서 연습한다. (4분)

## [슬라이드 65] 고쳐 달라고 말하고 다시 배포하기
- 유형: 실습
- 본문:
  1. 안내 문구나 문항 안내를 한 줄 바꿔 달라고 요청한다.
  2. 계획(무엇을 바꾸고 배포하는지)을 읽고 승인한다.
  3. 같은 주소를 새로고침해 바뀐 문구를 확인한다. 다시 배포해도 주소는 같다.
  - 오류가 나면 화면이나 콘솔의 문구를 그대로 Claude Code에 붙여 넣는다. 이 "오류 되돌려주기"가 오늘의 핵심 습관이다.
  - 선택 심화: 교사용 열람 화면을 요청해 본다.
- 프롬프트:
  ```
  학생 화면 맨 위의 안내 문구를 "답을 쓰고 저장 버튼을 누르세요"로 바꿔줘. 바꿀 내용을 먼저 설명하고, 같은 주소로 다시 배포해줘. 명령 실행은 내가 승인한 뒤에 해.
  ```
- 예상 결과: Claude Code가 바꿀 내용을 설명하고 승인을 요청한다. 배포가 끝난 뒤 같은 주소를 새로고침하면 새 문구가 보인다. 반영이 늦으면 다시 새로고침한다.
- 막힐 때:
  - 새로고침해도 문구가 그대로 → 배포가 끝났는지 확인하고, 안 바뀌면 화면 상태를 그대로 Claude Code에 전달한다.
  - 오류 문구가 나옴 → 문구 전체를 복사해 Claude Code에 붙여 넣고 "이 오류를 고쳐줘"라고 요청한다.
  - 배포 명령에서 권한 오류 → 63번 막힐 때(계정과 프로젝트 ID 확인)를 따른다.
- 노트: 5분 동안 "말로 고치고 다시 배포하는" 순환을 체험한다. 사람이 하는 일은 한 줄 요청과 승인이다. 배포는 같은 주소를 갱신하므로 짝에게 전한 주소가 바뀌지 않는다. 핵심은 오류 되돌려주기다. 화면이나 콘솔에 나온 오류 문구를 사람이 해석하려 하지 않고 그대로 Claude Code에 붙여 넣으면, 원인을 찾아 고치는 일을 Claude Code가 한다. 선택 심화인 교사용 열람 화면은 시간이 부족하면 연수 후 과제로 둔다. (5분)

## [슬라이드 66] 짝과 바꿔 점검하기
- 유형: 점검
- 본문:
  - 짝이 알려 준 배포 주소를 **내 브라우저**로 열어 4가지를 확인한다.
  - ① 교과 내용·문항이 단원 학습 목표와 맞는가 ② 로그인 없이 문항이 보이고 안내 문구가 이해되는가 ③ 글자 크기·접근성 ④ 개인정보와 정답이 페이지 소스에 없는가(오른쪽 클릭 > 페이지 소스 보기).
  - 남의 프로젝트에 내 계정으로 로그인하지 않는다. 문항과 안내를 보는 데까지만 한다.
  - 고칠 점은 짝이 자기 Claude Code에 요청한다.
- 막힐 때:
  - 주소가 열리지 않음 → 짝에게 주소를 다시 받고, 짝의 배포가 끝났는지 확인한다.
  - 페이지 소스가 읽기 어려움 → 정답이나 이름처럼 보이는 단어를 검색(Ctrl+F)해 본다. 판단이 어려우면 짝이 자기 Claude Code에 "이 웹앱 파일에 교사용 정답이나 개인정보가 있는지 알려줘"라고 요청한다.
  - 고칠 점이 나옴 → 짝이 자기 Claude Code에 요청하고, 고친 뒤 같은 주소에서 둘이 다시 확인한다.
- 노트: 서로의 화면을 보며 3분 동안 점검표를 채운다. 칭찬 하나, 고칠 점 하나를 말하게 한다. ①은 60번에서 본인이 본 것을 짝의 눈으로 다시 보는 것이다. 본인이 놓친 교과 내용 오류를 다른 교사가 발견하는 경우가 많다. ④는 이 프로젝트의 핵심 점검이다. 웹앱 파일은 누구나 페이지 소스로 볼 수 있으므로, 교사용 정답이나 개인정보가 거기에 있으면 공개된 것이다. 남의 프로젝트에 내 계정으로 로그인하지 않는 이유: 짝 프로젝트에 내 계정의 응답을 남기지 않기 위해서다. 테스트 계정 = Firebase 실습에 쓰는 개인 구글 계정(학생·업무 계정이 아닌 것). 점검이 늘어지면 ①과 ④를 먼저 하게 한다. (3분)

## [슬라이드 67] 오늘 만든 패키지 한 장 회고
- 유형: 정리
- 본문:
  - 만든 것 · 막힌 곳 · 다음 단원에 적용할 점을 한 장에 쓴다.
  - 공유: 배포 주소를 전하거나 `unit-project` 폴더를 압축한다. 공유 전에 개인정보와 비밀 키가 없는지 다시 본다.
  - 테스트 프로젝트 삭제는 M6 마지막 슬라이드(55번)를 따른다. 삭제하면 배포한 워크북 웹앱도 더는 동작하지 않으므로, 계속 쓰려면 삭제하지 않는다.
- 도식: 회고 한 장 카드. 위쪽 3칸 가로 배치. 칸 제목과 빈 줄:
  1. 만든 것: `unit-spec.md` · 하네스 팀(`.claude/`) · `slides.html` · `workbook/` · `firestore.rules` (체크 칸)
  2. 막힌 곳과 푼 방법: ______
  3. 다음 단원에 적용할 점: ______
  아래 띠 "공유 방법": 배포 주소 전달 / 폴더 압축 / 둘 다 하지 않음 중 선택 칸. 맨 아래 한 줄 "공유 전 확인: 개인정보 없음 · 비밀 키 없음".
- 노트: 한 줄씩만 쓰게 한다. "오늘 만든 것은 앱 한 개가 아니라, 내 교과 단원 하나를 수업 패키지로 만드는 절차입니다." 다음 단원에는 `unit-spec.md`만 새로 쓰고 하네스 팀을 다시 실행하면 같은 팀이 쓰인다. 서비스 계정 키 파일이나 AI 키가 폴더에 있다면 공유하지 않는다. 연수가 끝나면 M6 55번의 안내대로 테스트 프로젝트를 삭제할 수 있다. 삭제하면 배포한 워크북 웹앱도 더는 동작하지 않으므로, 계속 쓰려면 삭제하지 않는다. 이 슬라이드는 실습 시간으로 센다. 다음은 마무리(68번)다. (2분)
