## 1. `/lesson` 호출 이름: 통과
- M5 34: 프롬프트 "이름은 lesson", file-box `name: lesson`, 호출 `/lesson 함수와 매개변수`, 막힐 때 `name: lesson` 확인. 폴더는 `lesson-plan-writer`. 서로 일치한다.
- M5 35 `/lesson`(폴더 `lesson-plan-writer`), M3 17 노트 `/lesson`, M9 72 예시 4번 `/lesson`. 모두 `name: lesson`과 일치한다.
- 공식 근거(Skills 문서 재조회): "`name` sets the command that the `/` menu shows and that you type… **The directory name also invokes the skill.**" 표 예시는 "`.claude/skills/deploy-staging/SKILL.md` → `/deploy-staging`, or `/deploy` with `name: deploy`"이다. 따라서 `/lesson`은 동작한다.
- **권장(정확성):** 같은 근거에 따르면 폴더 이름(`/lesson-plan-writer`)으로도 부를 수 있다. 아래 두 문장은 폴더 이름으로는 부를 수 없다고 읽힌다.
  - M5 34 본문 2: "명령 이름은 폴더 이름이 아니라 `name` 값이다" → "`/` 메뉴에 보이는 명령 이름은 `name` 값이다(폴더 이름으로도 부를 수 있다)".
  - M3 15 노트: "`name`이 없을 때만 폴더 이름을 쓴다" → "`name`을 쓰면 그 이름이 명령이 되고, 폴더 이름으로도 부를 수 있다". 15 본문의 "명령 이름 = `name` 값(없으면 폴더 이름)"은 그대로 둬도 된다.
- **권장(정리):** M3 머리말 4행의 "M5가 (나)안이면 다시 맞춰야 한다", M9 검수 반영 13행의 "주의: M5 34가 (가)안을 택하면 이 줄도 `/lesson`으로 맞춰야 한다"는 이미 해결된 조건문이다. 빌더가 혼동하지 않도록 지운다.

## 2. hook `|| exit 2`: 통과
- M7 44 프롬프트 5행 "종료 코드 2로 끝나게", file-box `... | xargs -r python3 -m py_compile || exit 2`, 풀어 읽기, 단어 뜻, 노트가 서로 맞는다. 45 예상 결과("hook 오류 알림이 뜨고, 클로드가 오류 내용을 받아 스스로 고친다")와 노트("`|| exit 2` 없이 만든 hook이면 클로드는 모를 수 있다")도 44와 일치한다. 42 노트와 가정 15행도 같은 명령이다.
- 실행 결과(file-box JSON을 파싱한 명령을 그대로 사용):

| 입력 파일 | bash 종료 코드 | 출력 |
|---|---|---|
| `bad.py` (`def f(:`) | **2** | `File ".../bad.py", line 1` … `SyntaxError: invalid syntax` |
| `good.py` | 0 | 없음 |
| `note.md` | 0 | 없음 (grep 불일치 → `xargs -r`가 실행 안 함) |
| `bad.py`, `|| exit 2` 없는 원본 | 1 | 같은 SyntaxError |
| `bad.py`, `sh -c` | 2 | — |

- JSON 문자열의 `'\\.py$'`는 파싱하면 `'\.py$'`가 되어 의도대로 동작한다.

## 3. 58 원칙 1 · 57 규칙 · role: 통과 (모순 없음)
- 57 예시 규칙은 `users/{uid}`에 `allow read`만 있다. 58 원칙 1은 "자기 문서만 읽을 수 있다 + 고칠 때도 role은 바꿀 수 없다"이다. 57에는 쓰기 허용이 없으므로 role을 바꿀 길도 없다. 57 노트와 58 예상 결과("get 시험 결과는 57과 같아야")가 이 관계를 맞게 설명한다.
- `02_engineer_rules.md` D3의 users 규칙(update에서 `request.resource.data.role == resource.data.role`)과도 방향이 같다.
- **권장(노트 한 줄):** 58 노트의 "역할 지정은 사람이 하는 일 = 게이트"는 원칙 1보다 넓게 말한다. 원칙 1은 **고칠 때(update)** 만 막는다. 처음 문서를 만들 때(create) 본인이 role을 고르는 구조라면 새 계정에서 "teacher"를 고를 수 있다. 엔지니어 문서 D3도 이 한계를 적었다("role은 처음 로그인할 때 본인이 고른다… 실제 운영에서는 교사 명단… 추가"). 58 노트에 "처음 가입 때 고르는 role은 이 원칙으로 막지 못한다. 실제 운영에서는 교사 명단을 사람이 넣는다(심화)"를 한 줄 덧붙인다. 그리고 58 예상 결과의 "role 필드를 바꾸는 것을 허용하는 줄이 없는지"를 "만들기(create)·고치기(update)에서 role을 어떻게 다루는지"로 넓힌다.
- 참고(범위 밖, 경계면): `02_engineer_rules.md` 175행 users 규칙은 `allow get: if signedIn();`이다. 로그인한 누구나 uid를 알면 다른 사용자의 name·email을 읽을 수 있다. 덱 58의 원칙 1("자기 문서만")·원칙 3("request.auth != null만 검사하지 않는다")과 다르다. 덱은 "단순화한 예시"라고 밝혔으므로 원고 수정은 필요 없다. 다만 클래스룸 명세를 다시 다룰 때는 개인정보(email) 노출 경로로 검토해야 한다.
