# 02. 슬라이드 원고 M5: 하네스가 만든 파일 읽고 고치기 (슬라이드 29–35, 18분 + 휴식 33, 10분)

## 가정 및 작성 메모 (맨 위)
1. 개편 사유: 사용자 지시로 이 연수는 에이전트·스킬을 직접 설계하는 법이 아니라 `revfactory/harness`를 활용하는 법에 집중한다. 기존 M5(서브에이전트 파일 구조, 난이도 태깅 에이전트 만들기, 좋은 스킬 3원칙, SKILL.md 직접 작성, `/lesson` 호출)는 폐기했다. 원리 설명(Why-First, tools 최소 권한 원칙, description 작성 요령, 프런트매터 키 설명)은 쓰지 않는다. 구성 요소는 처음 나올 때 한 줄 정의만 쓴다.
2. 전제: M4(슬라이드 20–25)에서 하네스로 만든 퀴즈 팀(`quiz-writer`, `quiz-checker`, 오케스트레이터 스킬)이 현재 실습 폴더의 `.claude/` 아래에 있다. 실습 폴더 이름은 M4 원고의 `mini-harness`를 따랐다 `[확인필요: M4 압축 후 폴더 이름]`. 하네스가 만든 파일의 정확한 이름·개수·내용은 실행마다 다르므로 "예: ..."로 표기한다.
3. 불확실한 사실: (a) 이미 열린 세션에서 `.claude/agents/*.md`를 고친 뒤 바로 반영되는지, 재시작이 필요한지 `[확인필요]`. 반영되지 않으면 `/exit` → `claude`로 재시작하게 안내했다. (b) 오케스트레이터 스킬의 실제 이름과 실행 방식(자연어 요청 또는 슬래시 호출) `[확인필요]`. 그래서 실행은 M4 24번과 같은 문장형 요청으로 쓴다. (c) 공식 README(https://github.com/revfactory/harness) 대조는 이 작성 환경에서 열 수 없어 하지 못했다. 설치·사용 설명은 M4 원고(검수 확인분)와 브리프를 근거로 했고, 검수 단계에서 README와 대조해야 한다 `[확인필요]`.
4. 시간 검산: 개념 2분(26) + 실습 14분(27–30) + 점검 1분(31) + 정리 1분(32) = 18분. 슬라이드별 2+3+4+3+4+1+1 = 18분. 휴식 33은 10분이며 합계에 넣지 않는다.
5. 번호 규칙: 새 번호 체계(M4 = 20–25, M5 = 26–32, 휴식 33, M6 = 34–55)를 따른다. M4 슬라이드 참조는 23(말로 팀 만들기)·24(팀 실행·검수 결과)이다.

## [슬라이드 29] 하네스가 만든 폴더 지도
- 유형: 개념
- 본문:
  - 하네스가 만든 팀은 `.claude/` 폴더 안의 **마크다운 파일**이다. 파일을 열면 팀의 구성이 그대로 보인다.
  - 에이전트 = 역할이 정해진 하위 작업자를 정의한 파일(`.claude/agents/*.md`, 한 파일에 한 에이전트)
  - 스킬 = 재사용하는 작업 절차를 적은 파일(`.claude/skills/이름/SKILL.md`)
  - 오케스트레이터 = 팀의 실행 순서를 정한 스킬
  - 오늘은 이 파일들을 **읽고, 말로 고치고, 다시 실행**한다. 처음부터 쓰지 않는다.
- 도식: 폴더 트리 + 파일별 한 줄 정의 (이 슬라이드의 유일한 도식). 왼쪽에 트리, 오른쪽에 각 줄의 한 줄 정의를 화살표로 연결.
  ```
  mini-harness/
  └── .claude/
      ├── agents/
      │   ├── quiz-writer.md    ← 에이전트: 문항을 만드는 역할
      │   └── quiz-checker.md   ← 에이전트: 문항을 검수하는 역할
      └── skills/
          └── quiz-.../         ← 오케스트레이터 스킬: writer → checker 순서를 정한 절차 (예)
              └── SKILL.md
  ```
  트리 아래 주석: "파일 이름과 개수는 하네스가 실행마다 정한다. 위는 예시."
- 프롬프트: (없음)
- 예상 결과: (없음)
- 막힐 때: (없음)
- 노트: M4에서 하네스가 만든 파일의 위치를 지도로 한 번 보여 주는 슬라이드다. 구성 요소 정의는 한 줄씩만 말하고 원리 설명으로 들어가지 않는다. 핵심 메시지는 "하네스가 만든 것은 눈에 보이는 일반 파일이므로 열어서 읽고 말로 고칠 수 있다"이다. 파일 이름은 M4 26·27번 예시와 맞췄고 실행마다 다를 수 있다고 말한다 `[확인필요: 오케스트레이터 스킬 폴더의 실제 이름]`. (2분)

## [슬라이드 30] 실습: 생성된 파일 열어 보고 구조 설명받기
- 유형: 실습
- 본문:
  - M4에서 팀을 만든 폴더에서 Claude Code를 연다 (`cd mini-harness` → `claude`)
  - `!`로 시작하는 입력은 Claude Code 안에서 터미널 명령을 그대로 실행한다
  - 목록을 확인한 뒤, Claude Code에게 구조를 설명해 달라고 한다
- 도식: 2단계 가로 흐름: `! ls` 로 파일 목록 확인 → 말로 "3줄 설명" 요청.
- 프롬프트:
  Claude Code 입력창에서 목록 확인:
  ```
  ! ls .claude/agents .claude/skills
  ```
  이어서:
  ```
  .claude 폴더에 있는 에이전트와 스킬 파일을 읽고, 이 팀의 구조를 3줄로 설명해줘. 누가 무엇을 하는지와 실행 순서가 들어가게 해줘
  ```
- 예상 결과: `agents`에 `quiz-writer.md`, `quiz-checker.md` 같은 파일이, `skills`에 폴더가 하나 이상 보인다(예: 이름은 실행마다 다름). 설명은 "writer가 문항 생성 → checker가 검수 → 결과 정리" 같은 3줄이다.
- 막힐 때:
  - `ls`에 아무것도 안 나온다 → 팀을 만든 폴더가 아니다. `! pwd`로 위치를 확인하고 M4에서 쓴 폴더로 이동해 `claude`를 다시 연다.
  - `.claude` 폴더는 있는데 Claude Code가 에이전트를 모른다고 한다 → `/exit` 후 `claude`로 재시작한다 `[확인필요: 재시작 필요 여부]`.
  - 설명이 3줄보다 길다 → 정상이다. 그대로 읽고 다음으로 간다.
- 노트: 목록은 사람이 직접 확인하고 구조 이해는 Claude Code에게 맡긴다. 파일을 열고 싶은 참가자는 에디터로 `quiz-checker.md`를 열어 봐도 된다. 읽을 때 볼 것은 "역할 설명이 내 수업 맥락과 맞는가" 하나뿐이다. 문법이나 각 항목의 의미는 설명하지 않는다. (3분)

## [슬라이드 31] 실습: 말로 고치기
- 유형: 실습
- 본문:
  - 파일을 직접 편집하지 않는다. **고치고 싶은 점을 문장으로** 말한다.
  - 두 가지를 요청한다: ① 검수 기준 한 줄 추가 ② 만드는 문항 수 변경
  - 바뀐 곳만 보여 달라고 해서 **무엇이 바뀌었는지** 눈으로 확인한다
- 도식: 3단계 흐름: 말로 요청 → Claude Code가 파일 수정(승인) → "바뀐 줄만 보여줘"로 확인.
- 프롬프트:
  ```
  quiz-checker의 검수 기준에 "정답이 둘 이상으로 해석되는 보기는 반드시 지적한다"를 한 줄 추가하고, quiz-writer가 만드는 기본 문항 수를 5개로 바꿔줘. 파일을 고치기 전에 무엇을 바꿀지 먼저 알려줘
  ```
  수정이 끝나면:
  ```
  방금 바꾼 줄만 보여줘
  ```
- 예상 결과: 두 파일에서 각각 한두 줄이 추가·변경된 모습이 나온다(예: 검수 기준 목록에 한 줄 추가, 문항 수 숫자 3 → 5). 고친 파일 이름은 실제 생성된 이름을 따른다.
- 막힐 때:
  - 파일 수정을 승인하라는 화면이 나온다 → 정상이다. 바뀔 내용을 읽고 승인한다.
  - 기본 문항 수가 파일에 적혀 있지 않다고 한다 → 정상일 수 있다. "문항 수는 요청에서 정하게 두고, 따로 없으면 5개를 기본으로 한다는 문장을 추가해줘"라고 이어서 말한다.
  - 고친 뒤에도 다음 실행에서 예전 동작이 나온다 → `/exit` 후 `claude`로 재시작한다 `[확인필요: 재시작 필요 여부]`.
  - 오류 메시지가 나온다 → 읽으려 하지 말고 그대로 Claude Code에게 붙여 넣어 "이 오류를 고쳐줘"라고 한다.
- 노트: 이 슬라이드의 핵심은 "말로 요청하면 하네스가 만든 파일이 고쳐지고, 바뀐 곳은 확인할 수 있다"는 흐름이다. 사람이 하는 일은 승인과 확인이다. 검수 기준 문장은 자기 교과에 맞게 바꿔도 된다(예: "코드 예시는 실행 결과까지 확인한다"). (4분)

## [슬라이드 32] 실습: 고친 팀 다시 실행해 비교하기
- 유형: 실습
- 본문:
  - M4 27번에서 쓴 요청과 같은 문장으로 다시 실행한다
  - 이전 결과와 비교: 문항 수, 검수 지적의 달라진 점
- 도식: 좌우 2열 비교표. 왼쪽 "M4 실행 결과(3문항)", 오른쪽 "고친 뒤 결과(5문항)". 비교 항목: 문항 수 / 검수 지적 / 정답 해석.
- 프롬프트:
  ```
  이진 탐색 개념으로 객관식 퀴즈를 만들고 검수까지 맡겨줘
  ```
- 예상 결과: 문항이 5개로 나오고, 정답이 둘로 해석될 수 있는 보기가 있으면 검수 에이전트가 지적한다(예: 내용은 실행마다 다름). 지적이 없으면 검수 기준에 걸리는 문항이 없었다는 뜻일 수 있다.
- 막힐 때:
  - 문항이 여전히 3개다 → `/exit` 후 `claude`로 재시작하고 다시 보낸다 `[확인필요: 재시작 필요 여부]`. 그래도 같으면 "quiz-writer.md의 문항 수 부분을 보여줘"라고 해서 고쳐진 내용을 확인한다.
  - 검수 에이전트가 호출되지 않는다 → 문장 끝의 "검수까지 맡겨줘"를 그대로 쓴다. `.claude/agents/`에 `quiz-checker.md`가 있는지 확인한다.
- 노트: 고친 말이 실행 결과에 반영되는 것을 눈으로 확인하는 단계다. 결과 비교는 완벽한 일치가 아니라 "달라진 점이 있는가"만 본다. 출력은 실행마다 다르다. 시간이 남으면 "지적이 맞는지 내 판단은?"을 짝과 이야기한다. (3분)

## [슬라이드 33] 실습: 내 업무용 새 팀을 하네스에게 요청하기
- 유형: 실습
- 본문:
  - M4 26번과 같은 방식: **"하네스를 구성해줘" + 하고 싶은 일**을 문장으로 설명
  - 플랜 모드로 계획을 확인하고 승인한다 (`Shift+Tab`, 선택지는 "Yes, manually approve edits")
  - 오늘은 수업안 작성 도우미를 예로 든다. 내 업무에 맞게 바꿔도 된다.
- 도식: 입력 문장 → 플랜 모드 계획 확인 → 승인 → `.claude/` 아래에 파일 추가, 3단계 가로 흐름. M4 26번 도식의 축약판.
- 프롬프트:
  새 폴더에서 `claude`를 열고 (예: `mkdir lesson-helper && cd lesson-helper && claude`):
  ```
  하네스를 구성해줘. 단원과 학습 목표를 주면 수업안 초안을 쓰는 역할과, 초안이 학습 목표와 맞는지 검수하는 역할로 구성해줘. 검수는 파일을 고치지 않고 읽기만 해줘
  ```
- 예상 결과: 계획 화면에 만들 파일 목록이 나오고, 승인하면 `.claude/agents/`에 에이전트 파일 두 개와 `.claude/skills/`에 절차 스킬이 생긴다(예: 이름·개수는 실행마다 다름).
- 막힐 때:
  - 하네스가 아니라 일반 답변만 한다 → 플러그인 설치를 확인한다(M4 25번). 문장 맨 앞의 "하네스를 구성해줘"는 그대로 둔다.
  - 파일이 생겼는데 슬래시나 호출이 인식되지 않는다 → `/exit` 후 `claude`로 재시작한다 `[확인필요: 재시작 필요 여부]`.
  - 계획 승인 선택지가 다르게 보인다 → "Yes, manually approve edits"에 해당하는 항목을 고른다.
- 노트: 슬라이드 31의 "말로 고치기"를 새 팀에도 쓸 수 있음을 보여 주는 슬라이드다. 학생 실명·성적 같은 개인정보는 요청 문장에 넣지 않는다. 만들어진 팀을 실행하는 단계는 시간상 하지 않고 M7 프로젝트에서 본격적으로 한다. 파일이 생성되는 데 시간이 걸리는 참가자는 짝 화면을 함께 본다. (4분)

## [슬라이드 34] 점검: 하네스가 만든 것, 사람이 확인할 것
- 유형: 점검
- 본문:
  - [ ] 만들어진 내용(퀴즈·수업안)이 **내 교과 내용으로 맞는가**
  - [ ] 검수 기준이 **내가 중요하게 보는 기준과 맞는가** (맞지 않으면 말로 고친다)
  - [ ] 파일과 요청 문장에 **학생 개인정보가 없는가**
- 도식: 체크박스 3개 카드 가로 배열.
- 프롬프트: (없음)
- 예상 결과: 세 항목을 모두 확인했다.
- 막힐 때: 기준이 애매하면 슬라이드 31의 방식으로 검수 기준을 말로 추가한다.
- 노트: 사람이 확인할 것은 문법이나 파일 형식이 아니라 "무엇이 만들어졌는지"와 "내 교과 내용이 맞는지"다. 하네스가 만든 검수 에이전트가 있어도 교과 내용의 최종 판단은 교사의 몫이다. (1분)

## [슬라이드 35] 정리: 하네스로 만들고, 말로 고치고, 다시 실행

- 도식: 4칸 가로 흐름(요청 → 읽기 → 고치기 → 실행). 맨 오른쪽에 화살표로 "다음: Firebase(M6)".
- 프롬프트: (없음)
