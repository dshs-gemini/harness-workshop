## [슬라이드 42] 증거 없이 완료 없음
- 유형: 개념
- 본문:
  - "완료했습니다"라는 말이 아니라 **실행된 검증의 증거**(로그, 테스트 결과)가 있어야 완료다.
  - CLAUDE.md는 **부탁**(가끔 놓친다), hook은 **강제**(무조건 실행).
  - hook = 특정 이벤트(PreToolUse 등)에서 자동 실행되는 셸 명령으로, 결정적으로 실행된다.
- 도식: 좌우 2칸. 왼쪽 "CLAUDE.md = 부탁 → 깜빡할 수 있음", 오른쪽 "hook = 강제 → 이벤트마다 자동 실행". 위에 인용 박스 "증거 없이 완료 없음 (No evidence, no completion)".
- 노트: M3에서 "CLAUDE.md는 부탁이지 강제가 아니다"라고 예고했던 내용을 여기서 해결한다고 말한다. 원본 설명: 클로드의 말을 그대로 믿지 않고, 로그·테스트 결과·파일 diff 같은 물리적 증거가 남아야 완료로 인정한다. 예를 들어 "파일을 저장한 뒤에는 항상 문법 검사를 돌린다"를 CLAUDE.md에 적어 두면 클로드가 잊을 수 있지만, hook으로 등록하면 시스템이 강제로 실행하므로 잊을 수 없다. 이 증거가 사람 화면에만 뜨지 않고 클로드에게도 돌아가야 "증거 없이 완료 없음"이 지켜진다(44·45에서 확인한다). 질문을 던진다: "여러분 학교에서 '꼭 해 주세요'라고 부탁만 하고 확인은 못 하는 일이 있나요?" (2분)

## [슬라이드 43] hook이 울리는 주요 네 시점
- 유형: 개념
- 본문:
  - 클로드가 **일하기 직전·직후·기다릴 때·끝낼 때** 해당 이벤트에서 hook이 실행된다.
  - 오늘은 **PostToolUse**(도구 사용 직후) 하나만 쓴다.
- 도식: 표 4행. `PreToolUse` 도구 사용 직전 / `PostToolUse` 도구 사용 직후 / `Notification` 사용자의 입력·승인을 기다릴 때 / `Stop` 클로드가 작업을 마쳤다고 판단해 응답을 끝낼 때. PostToolUse 행을 강조색으로. 하단 모서리에 "심화 선택" 박스 한 칸(아래 문구).
- 심화 선택: **골든셋** = 기대 결과를 알고 있는 평가용 입력 집합. hook이 "매번 실행되는 검사"라면 골든셋은 기대 결과가 정해진 입력으로 정기 평가해 품질이 퇴보하지 않았는지 보는 회귀 테스트다. 오늘은 hook까지만 한다.
- 노트: 이벤트 이름은 대소문자까지 원본과 같게 쓴다. 공식 이벤트는 SessionStart, UserPromptSubmit, SubagentStop 등 30개 가까이 되며, 여기 표는 그중 주요 4종이다(검수 확인됨). 골든셋 예시(원본): `/quiz` 스킬을 고칠 때마다 미리 만든 5개 주제로 퀴즈를 생성시켜 정답 정확도가 이전과 같거나 나아졌는지 비교한다. 스킬이 여러 개로 늘어나는 시점에 고려해 볼 만하다고만 말하고 넘어간다. (1분)

## [슬라이드 44] 실습: hook 추가를 Claude Code에 시키기
- 유형: 실습
- 본문:
  - hook은 `settings.json`에 등록한다. 문법은 외우지 않고 **말로 시킨다**.
  - 목표: `.py` 파일이 저장될 때마다 자동 문법 검사.
- 프롬프트:
```
.claude/settings.json에 PostToolUse hook을 추가해줘.
Write나 Edit 도구로 .py 파일이 저장될 때마다, 그 파일에 대해
python -m py_compile 을 자동으로 실행해서 문법 오류를
바로 확인하도록 해줘.
문법 오류가 있으면 종료 코드 2로 끝나게 해서 클로드도 오류를 보고 고치게 해줘.
내 컴퓨터에 있는 명령(jq, python 또는 python3)을 먼저 확인하고 맞춰서 작성해줘
```
- 예상 결과: 아래와 비슷한 `.claude/settings.json`이 생긴다. **예시이며 내 컴퓨터에서는 다를 수 있다**(`python`이 `python3`, `jq` 대신 다른 방식 등).
```
.claude/settings.json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | grep '\\.py$' | xargs -r python3 -m py_compile || exit 2"
          }
        ]
      }
    ]
  }
}
```
  풀어 읽기 한 문장: "파일을 쓰거나 고칠 때마다(Edit|Write), 파일 경로를 확인해서(jq) .py 파일이면(grep) 파이선 문법 검사(py_compile)를 돌리고, 오류면 종료 코드 2로 끝내 클로드에게도 알려라(|| exit 2)."
  단어 뜻: jq = 설정 정보에서 파일 이름 꺼내기 / grep = 글자 걸러내기(.py로 끝나는 것만) / xargs = 앞에서 나온 결과를 다음 명령에 넘겨주기 / py_compile = 파이선 문법 검사 / 종료 코드 2 = 클로드에게 오류를 전달하는 신호.
- 막힐 때: 클로드가 설정을 다 쓰지 않고 질문하면 "내 컴퓨터 환경에 맞춰 알아서 정해줘"라고 답한다. 파일이 다르게 생겨도 `PostToolUse`와 `Edit|Write`가 들어 있으면 같은 뜻이다.
- 노트: 원본 대비 변경(검수 4-F): (1) 프롬프트에 "문법 오류가 있으면 종료 코드 2로 끝나게 해서 클로드도 오류를 보고 고치게 해줘"를 추가했고, 명령 끝에 `|| exit 2`를 붙였다. 이유: 원본 명령은 오류 때 종료 코드 1을 낸다. 공식 Hooks 문서상 종료 코드가 2가 아니면 사람 화면에 "hook error" 알림 한 줄만 뜨고 클로드는 stderr를 보지 못해, 오류를 모른 채 "완료"라고 말할 수 있다. 종료 코드 2여야 클로드가 오류를 받는다. macOS에서 직접 실행해 확인한 결과: 오류 파일은 종료 코드 2와 SyntaxError 전체 출력, 정상 .py 파일과 .md 파일은 종료 코드 0이었다(검수 보고서). (2) 프롬프트 끝에 "내 컴퓨터에 있는 명령(jq, python 또는 python3)을 먼저 확인하고 맞춰서 작성해줘"를 덧붙였다(설계서 허용). `xargs -r`은 macOS에서도 동작한다(검수 확인됨). `jq`의 Windows 기본 설치와 `python`/`python3` 이름은 미확인 `[확인필요]`이므로 위 문장으로 대응한다. 강사는 풀어 읽기 한 문장을 소리 내어 읽어 주고, 코드를 외울 필요가 없다는 점을 강조한다. (4분)

## [슬라이드 45] 실습: hook이 정말 울리는지 시험하기
- 유형: 실습
- 본문:
  - `/hooks`로 PostToolUse 항목이 보이는지 확인한다.
  - 일부러 **괄호 하나 빠뜨린** 코드를 만들게 해서 hook이 실행되는지 본다.
- 프롬프트:
```
/hooks
```
  이어서 다음 요청을 붙여넣는다.
```
practice.py 파일에 괄호를 하나 빠뜨린 파이선 함수를 일부러 만들어줘
```
- 예상 결과: `/hooks` 목록에 `PostToolUse` 항목이 보인다. 파일 저장 직후 hook이 자동 실행되어 hook 오류 알림이 뜨고, 클로드가 오류 내용을 받아 스스로 고친다. 이것이 **증거가 클로드에게 돌아간다**는 뜻이다. "완료"라고 말하기 전에 이미 문제가 드러나고 고쳐진다.
- 막힐 때: (1) `/hooks`에 항목이 없다 → 44번의 settings.json이 저장됐는지 확인한다. 설정 파일 직접 수정은 보통 자동 반영되므로(검수 확인됨) 재시작은 그래도 안 될 때의 대비책으로 `/exit` 후 `claude`를 다시 실행한다. (2) SyntaxError가 안 뜬다 → 슬라이드 48의 막힐 때 목록을 본다.
- 노트: 핵심 메시지는 "의도적으로 걸리는 상황을 만들어 테스트한다"이다. 오류가 뜨면 짝에게 화면을 보여 주게 한다. 문법 오류가 안 나는 정상 코드로도 한 번 시켜 보면 조용히 통과하는지 비교할 수 있다고 안내한다(시간이 남으면). 만약 `|| exit 2` 없이 만든 hook이라면 사람 화면에는 알림이 뜨지만 클로드는 오류를 모를 수 있다고 짚는다(44 노트). (4분)

## [슬라이드 46] 휴먼 리뷰 게이트: 모든 것을 자동화하지 않는다
- 유형: 개념
- 본문:
  - 자동화해도 좋은 것 vs **사람이 반드시 확인할 것**.
  - 게이트 = 사람이 검토·승인하는 단계(휴먼 리뷰 게이트). 미완성이 아니라 **의도된 설계**.
  - 다음 모듈 예고: Firebase 보안 규칙 게시와 배포가 대표적인 게이트.
- 도식: 카드 2장. 왼쪽(good) "자동화해도 좋은 영역": 문법·형식 오류 검사 / 정답이 명확한 사실 검증 / 양식 일치 여부 확인 / 초안 생성 그 자체. 오른쪽(bad) "반드시 사람이 확인해야 하는 영역": 학생 성적·평가 결과가 반영되는 최종 판단 / 개인정보가 포함될 가능성이 있는 데이터 / 학교 밖으로 실제 배포·공개되는 최종본 / 민감하거나 논쟁적인 주제를 다루는 교육 내용. 오른쪽 카드에 승인 게이트 아이콘.
- 노트: hook은 문법처럼 기계가 판정할 수 있는 것을 자동화하는 데 탁월하지만 전부를 맡길 수는 없다. M3 권한 슬라이드에서 "개인정보 폴더·실제 배포에 완전 자동 승인 금지"라고 했던 내용을 하네스 설계 원칙으로 정식화한 것이 휴먼 리뷰 게이트다. 보안 규칙·개인정보 데이터·성적 로직·실제 배포 전 최종 확인이 고위험 영역이다. 다음 모듈(M8)에서 Firebase 보안 규칙을 게시하고 배포할 때 이 게이트를 실제로 쓴다고 예고한다. (2분)

## [슬라이드 48] 막힐 때와 주의
- 유형: 정리
- 본문:
  - 오늘 손에 쥔 것: **자동 검증(hook) + 사람 승인 위치(게이트)**.
  - hook은 **의도적으로 걸리는 상황**으로 꼭 테스트한다.
  - 신뢰할 수 없는 곳의 hook 설정은 **복사하지 않는다**.
